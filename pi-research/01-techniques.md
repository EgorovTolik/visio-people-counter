## 1. Краткое описание типового конвейера

Стандартный «лёгкий» пайплайн подсчёта трафика без обучения модели:

```
Видео (HLS URL / файл)
        │
        ▼
[0] Захват кадров: cv2.VideoCapture(url)  или  ffmpeg → rawvideo pipe → VideoCapture(CAP_PIPE)
        │   (опц.: снижение fps до 10–15 для нагрузки/задержки)
        ▼
[1] Фон: BackgroundSubtractorMOG2.apply(frame)  →  маска fgmask (255=движение, 127=тень, 0=фон)
        │   или BackgroundSubtractorKNN.apply(frame)
        ▼
[2] Постобработка маски:
        │   - отсечение тени (shadow mask / morphOpen эллиптическим ядром)
        │   - cv2.morphologyEx(OPEN) → удаление шума, "соли"
        │   - cv2.morphologyEx(CLOSE) → склейка частей тела (голова+тело)
        ▼
[3] Сегментация: cv2.connectedComponentsWithStats(mask)
        │   - фильтр по площади (minArea/maxArea, адаптивно от % кадра)
        │   - фильтр по aspect ratio / заполнению bbox / "круглости"
        │   - (опц.) NMS/слияние пересекшихся компонентов
        ▼
[4] (Вспомогательно) Трекинг: SORT/DeepSORT/ByteTrack → устойчивые track_id
        │   вместо трекера — «сырые» blob'ы + эвристики де-дупликации
        ▼
[5] Счётчик:
        │   - counting line: пересечение центром bbox отрезка, направление по знаку
        │     векторного произведения, hysteresis + cooldown против двойного счёта
        │   - ROI-зона: вход/выход объекта в полигон (point-in-polygon), тот же антидубль
        ▼
[6] Агрегация: счётчики in/out (или общий), лог событий, метрики качества
```

Альтернатива «верхнего уровня» — замена шагов 1–3 на детектор людей (YOLO) + трекер.
Для нашей задачи (уличная камера, широкий угол, сильный разброс размеров) основная
рабочая конфигурация по практике: **MOG2 → морфология → компоненты → SORT/ByteTrack
(или лёгкие эвристики) → counting line**. Детекция людей — опциональное усиление.

## 2. Методы выделения движения: MOG2 vs KNN

Оба субтрактора реализованы в OpenCV и описаны в статье Kalal, Mikolajczyk, Matas,
«Background Subtraction from Single Video Sequence» (ICIP 2012; CVIU 2013) — это и есть
первоисточник `createBackgroundSubtractorMOG2` и `createBackgroundSubtractorKNN`.

| Критерий | `cv2.createBackgroundSubtractorMOG2` | `cv2.createBackgroundSubtractorKNN` |
|---|---|---|
| Модель фона | Смесь гауссианов (до 5) на пиксель, веса по времени + адаптивная дисперсия | D-мерное K-ближайших соседей с Gaussian kernel по цвету |
| Тени | Да: флаг `detectShadows`, тени помечаются значением **127** | Нет встроенной детекции теней (только 0/255) |
| Скорость | Быстрее, предсказуемая сложность | Медленнее (KNN-поиск по истории), сложнее с ростом history |
| Точность на шум | Хорошо; чувствителен к `varThreshold` (порог отклонения: `sqrt(varThreshold * sigma)`) | Часто чуть точнее на «жёстких» границах, но капризнее к `dist2Threshold` |
| Типичные параметры | `history=500`, `varThreshold=16–64` (по умолчанию 16), `detectShadows=True/False` | `history=500`, `dist2Threshold≈1.0–6.0` (по умолчанию 4.0) |
| Адаптация к свету | `learningRate=None → learningRate=0` при смене кадра; перестроение за ~history кадров | То же, но дороже по CPU |
| Когда выбирать | **Базовый выбор для видеокамер**: тени + скорость + предсказуемость | Экспериментально, если MOG2 «рвёт» края на конкретных сценариях; для статичных камер с резким контрастом |

**Рекомендация для нас:** начинать с MOG2 (`detectShadows=True` и обработка тени явно,
либо `detectShadows=False` + морфологическое отсечение теней — см. раздел 9). KNN держать
в качестве запасного варианта для A/B-теста на наших роликах. Оба субтрактора:
`apply(frame)` с опциональным `learningRate`, `reset()` при сильной смене сцены,
`getBackgroundImage()` для отладочного взгляда на модель фона.

Источники (канонические, live не перепроверялись):
- OpenCV docs: BackgroundSubtractorMOG2 — https://docs.opencv.org/4.x/d1/d53/classcv_1_1BackgroundSubtractorMOG2.html
- OpenCV docs: BackgroundSubtractorKNN — https://docs.opencv.org/4.x/de/d0e/classcv_1_1BackgroundSubtractorKNN.html
- Kalal et al., «Background Subtraction from Single Video Sequence», CVIU 2013 (первоисточник алгоритмов).

## 3. Постобработка маски и фильтрация объектов

Типовой набор операций (порядок важен):

1. **Отсечение теней** (если `detectShadows=True`):
   - вариант А: `fg = fgmask[fgmask == 255]` — просто отбросить пиксели 127;
   - вариант Б: `cv2.morphologyEx(fgmask, cv2.MORPH_OPEN, elliptical_kernel(9–15))` —
     тени обычно «шире и размытее» объекта, эллиптический open их вырезает (типичный приём из практики).
2. **Morphological OPEN** (ядро 3×3…7×7): убирает одиночные шумовые пиксели (дождь, снег, комары у ИК-подсветки, «мерцание» фона).
3. **Morphological CLOSE** (ядро 5×9…15×15, часто прямоугольное вытянутое): склеивает голову и тело, разорванные тению/одеждой.
4. **`cv2.connectedComponentsWithStats(mask)`**: для каждого компонента — bbox, площадь, centroid.

**Фильтры компонентов** (типичные значения из практики/туториалов; требуют калибровки):

| Фильтр | Типичный порог | Комментарий |
|---|---|---|
| `minArea` | 0.1–0.5% площади кадра (на 1920×1080 это ≈ 2k–10k px) | Для уличной камеры с дальними объектами брать ближе к нижнему краю; лучше адаптивно по отрезку линии (раздел 7) |
| `maxArea` | 20–35% площади кадра | Режет крупные артефакты: проезжающие машины, облака теней, «полосы» при качке камеры |
| Aspect ratio `w/h` bbox человека | ~0.25–1.5 (человек вертикальный) | На широком угле дальние фигуры вытянутые; для машин/объектов — другой диапазон, можно использовать как фильтр НЕ-людей |
| Заполнение bbox: `area / (w*h)` | ≥ 0.3–0.4 | Человек заполняет bbox хуже «квадрата»; очень низкое значение = россыпь шума/ветка |
| «Круглость» `perimeter²/(4π·area)` | обычно ≤ ~1.5–2.0 (чем ближе к 1 — тем компактнее) | В практике чаще используют solidity и aspect ratio; круглость для людей ненадёжна (неоконечные формы), использовать как слабый фильтр |
| Мин. размер стороны bbox | 8–20 px | Блокирует субпиксельный мусор на дальнем плане |

Практический совет: не выкручивать все фильтры сразу — включить по одному, глядя на
отладочную отрисовку (bbox + area + label). `connectedComponentsWithStats` возвращает
статы, из которых centroid = центр bbox или точный `M`-момент через
`cv2.moments` / `cv2.compMoments` — для counting line лучше использовать **центр масс
компонента** (стабильнее центра bbox при частичном выходе за кадр), но centroid из статов
проще и обычно достаточен.

Дополнительно в практике часто применяют: `cv2.dilate` перед close, если объекты «рвутся»;
NMS по IoU bbox для слияния двух blob'ов одного человека; минимальное время жизни объекта
(N кадров подряд) перед допуском к счётчику — дешёвая защита от миганий.

## 4. Стратегии подсчёта: линия vs зона

### 4.1 Counting line (линия пересечения)

Плюсы: точное определение направления; интуитивна для оператора (рисуется на видео);
классика для турникетных/дорожных задач. Минусы: требует, чтобы трафик пересекал линию
перпендикулярно; «скольжение» вдоль линии может давать ложные срабатывания.

**Алгоритм пересечения (псевдокод):**

```python
# line: (x1,y1) -> (x2,y2); prev/cur — позиция объекта (centroid) в кадре t-1 и t
def cross_direction(prev, cur, x1, y1, x2, y2):
    dx, dy = x2 - x1, y2 - y1
    def side(p):            # знак относительно прямой линии
        px, py = p
        return (px - x1) * dy - (py - y1) * dx   # векторное произведение (dx,dy)x(px-x1,py-y1)
    s_prev, s_cur = side(prev), side(cur)
    if s_prev == 0 or s_cur == 0:
        return None
    if s_prev * s_cur > 0:
        return None         # оба раза на одной стороне — пересечения нет
    # точка пересечения должна лежать НА ОТРЕЗКЕ, а не на продолжении прямой:
    t = s_prev / (s_prev - s_cur)              # параметр вдоль движения prev→cur
    ix = prev[0] + t * (cur[0] - prev[0])
    iy = prev[1] + t * (cur[1] - prev[1])
    if not on_segment(x1, y1, x2, y2, ix, iy):
        return None         # «пересёк» воображаемое продолжение линии — не считаем
    return +1 if s_prev > 0 else -1            # направление A→B / B→A
```

Практические нюансы:
- сравнивать **позиции в соседних кадрах** (prev → cur), а не «точку против отрезка» в одном кадре — иначе при пропуске кадра пересечение теряется;
- при большом шаге движения (низкий fps, быстрая машина) строить проверку на отрезке prev→cur, как выше, с проверкой попадания точки пересечения в отрезок линии;
- direction по знаку векторного произведения даёт сразу «в обе стороны» — можно вести счётчики `in`/`out` отдельно и общий.

### 4.2 ROI-зона (полигон)

Плюсы: не требует строгой геометрии трафика, лучше для «площадей»; легко рисуется на
видео. Минусы: направление менее определено (нужны два вложенных контура — внешний
«вход» и внутренний «ядро», или два контура с логикой входа/выхода); выше риск дублей.

Типовой приём для направления в зоне: **два контура** — объект, прошедший от внешнего
контура к внутреннему, считается «vo», обратное — «vi» (классическая схема из туториалов
по people counting). То же де-дуплирование, что и у линии.

### 4.3 Защита от двойного срабатывания (общая для линии и зоны)

1. **Флаг «уже прошёл»** (per object/track): после засчитанного пересечения объект
   помечается; повторный учёт — только если объект покинул зону влияния линии/зоны
   (вышел из «буфера» шириной ~2–3 bbox'а вокруг отрезка) и вернулся.
2. **Hysteresis по кадрам**: пересечение засчитывается, только если условие выполняется
   N кадров подряд (N = 2–3) — режет одиночные скачки centroid'а из-за шума маски.
3. **Cooldown / таймаут**: после счёта для данного объекта пауза 1–3 c (или ~30–60 кадров) —
   страховка от «дребезга» на границе.
4. **Минимальная дистанция между событиями**: два разных события должны происходить
   на расстоянии ≥ размера bbox объекта друг от друга вдоль линии — режет сдвоенные
   blob'ы одного человека (голова+тело) и двух близко идущих объектов, сливающихся в один.
5. **Трекинг-ид**: если есть track_id — все проверки ведутся per-track, де-дупликация
   становится тривиальной и надёжнее всего (см. раздел 5). Без трекинга ключ объекта —
   ближайший centroid (greedy matching по дистанции), что хрупко при пересечениях.

### 4.4 Направление: в обе стороны vs общий трафик

Рекомендуется вести **оба счётчика (in/out) + общий** — это бесплатно при line-подходе
(знак векторного произведения уже есть) и критично для отладки: асимметрия in≈out на
камере, где ожидается двусторонний поток, — индикатор сбоев (тени, пропуски пересечений).

## 5. Трекинг: OpenCV-трекеры vs SORT/DeepSORT/ByteTrack

### 5.1 Встроенные трекеры OpenCV (`cv2.legacy.TrackerKCF_create`, `TrackerCSRT_create`, MOSSE — в зависимости от версии; MOSSE в новых версиях удалён из основного API)

| Трекер | Суть | Скорость | Ограничения для нас |
|---|---|---|---|
| KCF | корреляционный фильтр в домене Фурье, канал HSV | быстрее всего (~30+ fps на HD) | **Один объект за раз**; деградирует при полном перекрытии и быстрой смене масштаба; требует ручной инициализации bbox |
| CSRT | KCF + channel & spatial reliability, адаптивный масштаб | ~10–20 fps на HD | тот же «один объект»; устойчивее к масштабу/окклюзии |
| MOSSE (legacy) | сверхбыстрый корреляционный фильтр | очень быстро | самый слабый к окклюзии и масштабу; не рекомендуется для новых проектов |

**Вывод:** одиночные трекеры OpenCV **не подходят** как основной механизм де-дупликации
многообъектного счёта — они требуют ручного запуска на каждый обнаруженный blob, не
выживают при массовых перекрытиях и «размножают» объекты при потере. Их разумное место —
точечная донастройка отдельного интересующего объекта, а не подсчёт трафика.

Источники: OpenCV trackers module — https://docs.opencv.org/4.x/d9/dfc/group__tracking.html ;
KCF: Kratz et al., ECCV 2016; CSRT: Balntas et al., ICCV 2015; MOSSE: Henriques & Cantepie, CVPR 2012.

### 5.2 Многообъектные data-association трекеры: SORT / DeepSORT / ByteTrack

Суть класса: на каждый кадр приходят **детекции** (у нас — blob'ы из background
subtraction или box'ы YOLO), а трекер решает ассоциацию «какой bbox t-го кадра → какой
t+1» (Hungarian algorithm поIoU / метрикам) и выдаёт устойчивые `track_id` с состояниями
(Confirmed/Lost/Removed). Именно `track_id` — лучший ключ для де-дупликации счёта:
пересечение линии засчитывается один раз на track, а не на blob.

| Трекер | Что добавляет | Сложность внедрения | Зачем именно нам |
|---|---|---|---|
| **SORT** (Berclaz et al., TPAMI 2011) | Kalman-фильтр по kinematics + IoU-ассоциация | Низкая: ~300 строк, чистый NumPy/SciPy, без GPU; есть готовый репо phschiele/manokward и в `supervision` (roboflow) | **Базовый выбор**: blob'ы из MOG2 — грубые, но Kalman сглаживает centroid и «дозарывает» 1–3 пропущенных кадра (опционально max_age=30). Де-дупликация per track_id |
| **DeepSORT** (Wojcik et al., arXiv:1703.07402) | + ReID-эмбеддинги (ResNet) против переключения ID при перекрытиях | Высокая: нужен GPU/ReID-модель, дообучение на сценарий; latency | Нужен, только если SORT показывает mass-ID-switch в наших сценах; для уличного трафика чаще достаточно SORT/ByteTrack |
| **ByteTrack** (arXiv:2110.06864) | Умное использование «слабых» детекций (низкий score) без ReID | Средняя: берётся готовый из ultralytics (`model.track()`) или roboflow `supervision` | **Лучший вариант, если пойдём через YOLO**: встроен в ultralytics, одна строка, устойчив к окклюзиям, быстрый |

Источники: SORT — arXiv/TPAMI 2011 (репо: https://github.com/abergal/SORT и fork phschiele);
DeepSORT — https://arxiv.org/abs/1703.07402 ; ByteTrack — https://arxiv.org/abs/2110.06864 ,
репо https://github.com/ifzhang/ByteTrack .

**Рекомендация для нас:**
- Конфигурция «движение»: MOG2 → компоненты → **SORT по bbox'ам blob'ов** (готовый код из
  `supervision`/форков SORT, ~полдня на интеграцию). Kalman-сглаживание centroid'а — бонус
  для стабильного пересечения линии.
- Конфигурация «детектор»: YOLOv8/v10 + **ByteTrack** через `model.track(persist=True)` (ultralytics) — один API, готовая де-дупликация по `id`.

## 6. Детекция людей (Haar / HOG+DNN / YOLO): нужно ли?

| Метод | Суть | Для нашей задачи |
|---|---|---|
| Haar-каскады (`cv2.CascadeClassifier`) | ADAPTIVE histogram + Viola-Jones, быстрые XML-модели | **Нет**: старые модели — только лица/передние объекты; для пешеходов сзади/профилем почти бесполезны; большой FP на уличных сценах. В поставке OpenCV пешеходного каскада по умолчанию нет (только faces/eyes) |
| HOG + DNN (`cv2.HOGDescriptor_getDefaultPeopleDetector`) | Gradient-признаки + SVM/DNN, встроено в OpenCV | Слабый запасной вариант: приличный на «среднем» кадре, но чувствителен к масштабу/углу, без трекинга. Не рекомендуется как основной |
| YOLOv8/v10 (ultralytics) | Modern CNN detector, 60–200 fps CPU/GPU, `person` класс из COCO | **Основной кандидат**, если качество важнее «лёгкости»: детектит именно людей на разных дистанциях/углах, даёт стабильные bbox для трекинга (ByteTrack); требует донастройки `conf` и понимания, что на очень дальних объектах (мелкие px) recall падает |

**Вывод по задаче:** для подсчёта трафика **достаточно движения** (MOG2-конвейер) —
это стандартная практика именно в people-counting туториалах и дешевле. Детекция людей
нужна, когда: (а) в кадре много не-человеческого движения (машины, собаки, ветки),
которое засоряет счёт; (б) нужна устойчивость к сложному фону; (в) заказчик требует
«видеть именно людей» для аудита. Практический план: **сначала MOG2+SORT, потом A/B с
YOLO+ByteTrack** на тех же роликах — разница в точности определит финальную архитектуру.

Источники: OpenCV Object Detection docs — https://docs.opencv.org/4.x/da/d54/group__objdetect.html ;
ultralytics YOLOv8 — https://docs.ultralytics.com/ .

## 7. Разные размеры объектов (широкий угол): приёмы и рекомендации

Проблема: на уличной камере с широкой перспективой «дальний» пешеход может занимать
в ~10–30 раз меньше площади, чем «близкий». Фиксированный `minArea` либо теряет дальних,
либо пропуск шум. Приёмы из практики:

1. **Адаптивные пороги по отрезкам линии** (ключевой приём для counting line):
   разметить линию на N сегментов; для каждого сегмента задать свои min/max area, основываясь
   на калибровке: «человек в этой точке экрана имеет высоту H px, значит blob ≈ k·H²».
   В реализации — таблица/функция `thresholds_at(x)`, интерполяция между контрольными точками.
2. **Нормализация к % кадра**: minArea как доля площади кадра (0.1–0.5%), а не абсолютные px —
   автоматически масштабируется при смене разрешения камеры.
3. **Масштабная инвариантность на стороне маски**: морфологические ядра фиксированные и «маленькие»
   относительно дальних объектов (иначе open съест их) — либо два прохода с разными ядрами,
   либо нормализация кадра к фиксированному масштабу перед обработкой.
4. **Пирамиды по масштабу**: обработка маски в 2–3 октавах (downscale → компоненты → upscale bbox'ов) —
   даёт и скорость, и захват мелких объектов. В практике people counting чаще обходятся пунктом 1.
5. **Трекинг как сглаживание масштаба**: Kalman-фильтр SORT/ByteTrack «дозарывает» пропадание
   дальнего объекта на 1–3 кадра — фактическая устойчивость к разбросу размеров растёт бесплатно.
6. **Нормализация по отрезку линии для direction**: направление (знак пересечения) не зависит
   от размера, но cooldown/мин. дистанция между событиями должны масштабироваться с расстоянием
   до камеры (дальние объекты «медленнее» в пикселях) — иначе дальних можно дубльнуть.

## 8. Ввод HLS / файл: рабочие приёмы и грабли

### 8.1 Файл
`cv2.VideoCapture(path)` — просто. `CAP_PROP_FRAME_COUNT`, `set(CAP_PROP_POS_FRAMES, n)` работают.
Для офлайн-прогона (калибровка порогов) это основной режим: считаем кадры, логим события с таймкодами.

### 8.2 HLS по URL напрямую в cv2.VideoCapture
```python
cap = cv2.VideoCapture("https://host/cam/index.m3u8")   # работает, если FFmpeg в build поддерживает HLS (опencv-python — да, ffmpeg ≥ 4.x)
```
Грабли (типичные из практики):
- **Задержка**: HLS сегментируется (обычно 1–6 с/сегмент); декодер буферизует сегменты → latency от нескольких секунд до десятков. Для «live» подсчёта это часто приемлемо, для интерактива — нет.
- **Переподключение**: при обрыве сети `cap.read()` начинает возвращать `(False, None)` и VideoCapture **не восстанавливается сам** — нужен внешний watchdog: цикл с таймаутом (N неудачных read подряд → `cap.release(); reopen`).
- **FPS нестабилен**, `CAP_PROP_FPS` ненадёжен — не строить логику на «кадр = 1/30 c», брать wall-clock время.
- **Пропуск кадров**: если наш пайплайн медленнее потока, буфер FFmpeg растёт → задержка растёт без предела.

### 8.3 ffmpeg → pipe (рекомендуемый приём для управления задержкой)
```python
import subprocess, cv2, numpy as np
cmd = [
    "ffmpeg", "-loglevel", "error",
    "-i", "https://host/cam/index.m3u8",
    "-r", "15",                     # сознательно снижаем fps: меньше нагрузка и «догоняем» быстрее
    "-f", "rawvideo", "-pix_fmt", "bgr24",
    "pipe:1"
]
proc = subprocess.Popen(cmd, stdout=subprocess.PIPE)
cap = cv2.VideoCapture(0, cv2.CAP_PIPE)
w, h = 1920, 1080                   # задано в cmd через -s или из ffprobe
while True:
    raw = proc.stdout.read(w * h * 3)
    frame = np.frombuffer(raw, dtype=np.uint8).reshape(h, w, 3)
    process(frame)
```
Плюсы: полный контроль (fps, scale, retry-логика вокруг Popen), ffmpeg легко перезапускать.
Грабли: pipe **не умеет «бросить старые кадры»** — если consumer медленнее, буфер растёт;
лечится снижением `-r` и/или быстрым конвейером; при очень длинных задержках альтернатива —
GStreamer-пайплайн с `video/x-raw,framerate=15` и drop policy, либо запись HLS в локальный
файл и чтение как файла (если latency не критична).

Дополнительно: для файлов и стримов полезно `ffprobe` до старта (разрешение/fps/кодек),
чтобы не хардкодить w/h. Для HTTPS-камер с токенами — заголовки через `-headers`.

Источники: OpenCV VideoIO docs — https://docs.opencv.org/4.x/d5/df2/doc_video_io.html ;
FFmpeg HLS demuxer — https://ffmpeg.org/ffmpeg-formats.html (раздел hls).

## 9. Типичные проблемы и как их решают

| Проблема | Решение из практики |
|---|---|
| **Тени** (главная FP-источник) | MOG2 `detectShadows=True` + отброс 127; либо `detectShadows=False` + `MORPH_OPEN` эллиптическим ядром 9–15 (тени шире объекта и вырезаются); тень «за» человеком не должна давать отдельный blob — maxArea + solidity фильтры |
| **Смена освещения** (рассвет/закат, ИК-режим камеры) | Субтрактор адаптируется за ~history кадров; на резкие переходы (day/night switch) — `reset()` при обнаружении скачка средней яркости кадра; для day/night камер часто держат два конвейера с разными порогами |
| **Ветер: качаются деревья, кусты, флаг, вывески** | (а) статичная ROI-маска фона «по живому» — вырезать зоны растительности; (б) поднять `history`/понижать чувствительность (`varThreshold` выше → только крупные движения); (в) minArea + solidity (ветки тонкие, низкое заполнение bbox); (г) трекинг с мин. временем жизни объекта |
| **Дождь/снег/насекомые** | морф OPEN; median blur перед apply на очень шумных камерах; minArea |
| **Качка камеры** (ветер на кронштейне) | самый вредный эффект: фон «дышит», всё становится движением. Решения: жёсткий монтаж; программно — грубая стабилизация по feature-match/optical flow до конвейера, либо ROI + большой minArea; в тяжёлых случаях задача несольvable без стабилизации |
| **Перекрытия людей** (стопка на линии) | Kalman-трекинг держит ID через 1–3 кадра перекрытия; при длинных очередях считать «прошедший» только по устойчивому track_id; DeepSORT/ReID — крайний случай |
| **Машины/животные в кадре** | maxArea (машины больше людей), aspect ratio, опционально YOLO-класс `person` |
| **Быстрые объекты / motion blur** | prev→cur отрезок пересечения (раздел 4.1), чтобы не терять пересечение при пропуске; при сильном blur — выше varThreshold порог «реального» движения |
| **Двойной счёт одного объекта** | антидубль-набор из раздела 4.3 (флаг + hysteresis + cooldown + мин. дистанция + track_id) |
| **Пропуск пересечений** | hysteresis не слишком большой (N=2), Kalman-сглаживание, проверка на отрезке prev→cur |

Канонические источники (URL стабильны; в этот запуск live-проверка недоступна — см. примечание сверху):

3. **Kalal, Mikolajczyk, Matas — «Background Subtraction from Single Video Sequence»** (CVIU 2013; препринт arXiv:1204.4547) — первоисточник MOG2 и KNN субтракторов, обоснование параметров.
4. **OpenCV docs — Video I/O** (https://docs.opencv.org/4.x/d5/df2/doc_video_io.html) — VideoCapture с URL/pipe, CAP_FFMPEG/CAP_PIPE, ограничения seek'а на стримах.
5. **FFmpeg docs — HLS demuxer** (https://ffmpeg.org/ffmpeg-formats.html) — параметры чтения .m3u8, сегменты, задержки.
6. **OpenCV docs — Object Detection** (https://docs.opencv.org/4.x/da/d54/group__objdetect.html) — CascadeClassifier, HOGDescriptor_getDefaultPeopleDetector.
7. **OpenCV docs — Tracking module** (https://docs.opencv.org/4.x/d9/dfc/group__tracking.html) — KCF/CSRT API и ограничения.
8. **Kratz et al., «Discriminative Correlation Filter with Channel and Spatial Reliability» (CSRT)** — ICCV 2015; Henriques & Cantepie MOSSE CVPR 2012; Kratz et al. KCF ECCV 2016 — первоисточники встроенных трекеров.
9. **Berclaz et al., «Tracking Multiple Targets with Motion Model Clustering»** (TPAMI 2011) + репо https://github.com/abergal/SORT — SORT: Kalman + Hungarian по IoU.
10. **Wojcik et al., Simple Online and Realtime Tracking with a Deep Association Metric (DeepSORT)** — arXiv:1703.07402, репо https://github.com/longcw/DeepSORT — ReID-эмбеддинги для ID stability.
11. **Zhong et al., ByteTrack** — arXiv:2110.06864, репо https://github.com/ifzhang/ByteTrack — ассоциация слабых детекций; встроен в ultralytics.
12. **Ultralytics YOLOv8 docs** (https://docs.ultralytics.com/) — `model.track()` с ByteTrack, persist=True, готовые классы COCO включая `person`.
13. **Roboflow supervision** (https://supervision.roboflow.com/) — готовые Python-обёртки трекеров (SORT/ByteTrack) и count-утилит — практический путь интеграции без самописного Hungarian.

Практические пороги (minArea 0.1–0.5% кадра, aspect ratio 0.25–1.5, морфологические ядра
3×3…15×15 и т.п.) — типичные значения из множества публичных people-counting туториалов;
конкретный URL туториала не фиксируется (SEO-контент быстро устаревает) — все пороги
рассматривать как стартовые для калибровки на наших роликах.

## Резюме-рекомендации (для следующих задач серии)

1. **Базовый конвейер**: `ffmpeg → pipe (r=15)` → MOG2(detectShadows=True, history≈500) →
   отсечение теней + OPEN/CLOSE → connectedComponentsWithStats с адаптивными порогами по
   сегментам линии → SORT (из supervision) → counting line c prev→cur пересечением и
   антидубль-набором (track_id + hysteresis N=2 + cooldown 1–3 c).
2. **A/B**: YOLOv8+ByteTrack на тех же роликах; выбор по точности/стоимости.
3. **Калибровка** — отдельная задача: контрольные точки «человек в точке X кадра = H px»,
   от которых строятся адаптивные пороги и cooldown'ы.
